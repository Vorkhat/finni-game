# Архитектура

## Основной runtime

```text
UI (SolidJS screens/components)
          ↓
GameService (apps/web application layer)
          ↓
Shared Domain (packages/shared)
          ↓
StorageAdapter (apps/web)
          ↓
Local Storage

packages/content ── definitions ──→ application/domain
apps/api ── optional future infrastructure; not in the gameplay path
```

**Mandatory gameplay has zero backend dependency.**

UI отвечает за отображение и команды пользователя. `GameService` последовательно вызывает доменные операции и сохраняет новый снимок профиля. Он не содержит финансовых формул. `packages/shared` не импортирует SolidJS, браузерные API или backend-код: операции получают состояние и команду и возвращают новое состояние либо контролируемый `DomainError`.

## Источник истины

- Бизнес-правила, инварианты, расчёт результата периода и прогресс питомца: `packages/shared`.
- Контент и детские тексты обратной связи: `packages/content`.
- Оркестрация и локальный adapter: `apps/web/src/application`.
- `apps/api`: самостоятельный экспериментальный модуль без зависимости со стороны web.

## Persistence и версии

`StorageAdapter` определяет `loadProfile`, `saveProfile`, `deleteProfile`, `resetProfile`, `hasProfile`. Основная реализация использует `localStorage`; тестовая — память. При загрузке вызывается `migrateProfile`. Текущая версия схемы — `2`; versionless/v1 мигрируют без сброса, неизвестная или повреждённая структура возвращает `INVALID_PROFILE`, а не попадает в игру.

Этап 4 разделяет физическое хранение: `finni.game-profile` для обычной игры и `finni.demo-profile` для демо. Ключ `finni.profile-mode` содержит только активный режим. Переключение создаёт новый `GameService` над нужным adapter namespace; обычный снимок не копируется и не перезаписывается. Delete обычного профиля также удаляет неактивный demo save, reset создаёт новый начальный профиль, а demo reset вызывает детерминированный `resetDemoProfile`.

## Безопасность состояния

Компоненты не меняют профиль напрямую. Все денежные команды проходят через доменные операции, проверяют остатки и создают `Transaction`. Подтверждённый план заменять нельзя. Demo Mode использует детерминированный профиль и не зависит от часов или сети.

## UI Этапа 1

`GameProvider` создаёт `GameService` и загружает профиль до показа маршрутов. Boot скрывает промежуточное состояние, затем guard выбирает onboarding, незавершённый выбор цели или Home. Signal профиля — опубликованный результат сервиса для отображения; формы хранят только ещё не подтверждённый выбор/имя. Компоненты не пересчитывают экономику. Прогресс цели вызывает `calculateGoalProgress` из shared.

`GameService.commit` сначала сохраняет профиль, затем публикует состояние: ошибка localStorage не выдаёт несохранённый профиль за успешный. `selectGoal` сверяет id с контентным каталогом. При сбое загрузки показывается экран повторной попытки, без удаления данных. Повтор обучения не создаёт новый профиль.

Маршруты первого запуска: `/boot`, `/onboarding`, `/pet/create`, `/goal/select`, `/home`, `/settings`. Browser Back возвращает шаг знакомства; возврат к созданию уже существующего питомца блокируется guard.

`assets/registry.ts` централизует пути локальных WebP. Resolver использует species/colorVariant/stage/emotion: fallback сначала на idle той же стадии, затем на idle предыдущей доступной стадии, всегда в пределах species/colorVariant. Отсутствие стадии даёт dev warning. Неподдерживаемая внешность старых тестовых профилей (например fox) отображает пояснение, сохраняя данные. Она не подменяется котом или драконом.

Настройки звука/анимаций относятся к устройству и хранятся отдельно от финансового профиля. Системный `prefers-reduced-motion` имеет приоритет. Звук на этапе 1 — сохранённая настройка, без аудиопакета.

E2E запускает только production web-preview; внешние и `/api` запросы блокируются и считаются ошибкой теста. PWA service-worker и Android bundle не входят в текущий runtime.

## Активный день — Этап 2

`/day/start` объясняет доход из `packages/content/economy.json`. Команда начала вызывается только по нажатию, никогда при монтировании или reload. `/budget` сохраняет изменения черновика через `setPlan`; после `confirmPlan` работает в read-only режиме с derived preview плана/факта. Доход начисляется один раз, plannedSavings не переводятся автоматически.

`/shop` использует каталог товаров, подтверждение и `purchase`. Нехватка денег — доступный сценарий с объяснением и переходом к заданиям. История выводится из транзакций текущего периода. `/savings` использует preview депозита/снятия и отдельное подтверждение; preview не меняет профиль. `/tasks` и `/tasks/:id` выводят шесть существующих определений через общий TaskRenderer. `/progress` остаётся навигационной основой. `/day/result` — переходный экран без вызова closePeriod; итог и следующие периоды относятся к Этапу 3.

`evaluateTask` — чистая функция shared. UI хранит только временный выбор/корзину/распределение; суммы, последствия и успех вычисляет домен из определения и проверенного TaskSubmission. Симуляция не получает GameProfile. При получении награды GameService вызывает `completeTask`, который повторно проверяет ответ и создаёт TASK_REWARD только один раз. Неверные решения можно пересматривать без списаний. Шесть типов используют три общих вида управления: распределитель, корзину и карточки действий, а не шесть независимых экранов.

`GameService.commit` блокирует пересекающиеся сохранения до завершения операции и вычисляет новое состояние внутри блокировки. UI использует busy/disabled и меняет подтверждение на результат. Повторный transactionId отвергается доменом; повторная награда также защищена taskId. Экран награды кратко блокирует новые ссылки, чтобы второй клик не попал в появившуюся кнопку перехода. Все DomainError преобразуются централизованно в `error-messages.ts`.

Игровые разделы имеют собственную прокрутку между header и нижней навигацией. Диалоги ограничены высотой viewport. Реакция happy существует только на экране обратной связи и исчезает при уходе; resolver сохраняет безопасный idle для дракона, у которого нет happy-файла.

## Законченный цикл — Этап 3

`/day/result` заменяет переходный экран Этапа 2: confirmation → GameService.finishPeriod → shared.closePeriod → одна атомарная запись профиля → сохранённый результат. `/day/result/:id` показывает конкретный snapshot из periodHistory, в том числе при активном следующем дне. `/progress` показывает стадию, дни, цель, накопления, LearningProgress и историю.

Следующий день открывается через существующий DayStart. При смене стадии перед Home/стартом срабатывает `/day/evolution`; acknowledgement через сервис сохраняет evolutionSeen. Reload до подтверждения возвращает к ещё не просмотренному достижению; после подтверждения не повторяет celebration. CSS transforms/opacity и локальные production assets не требуют анимационных библиотек; reduced-motion и настройка отключения анимаций поддерживаются.

`PeriodExtras` выводит EventCard и GoalAchievement. GameService сверяет событие с content-последовательностью, shared.resolveDecisionEvent вычисляет изменения и защищает от повторов. Тексты feedback и последовательность заданий/событий находятся в content. Все шесть заданий доступны прежним путём независимо от рекомендации дня.

Ни API, ни сетевой источник времени, ни серверные timestamps не участвуют в пятидневном цикле. Demo Mode использует те же UI-команды и доменные операции, но отдельное хранилище. `/adult` защищён локальным доступным long press и показывает производные данные существующего `LearningProgress`; reset/delete идут через GameService. Guard закрывает прямой вход в result/evolution/adult dashboard без нужного состояния. ErrorBoundary скрывает stack trace, а повреждённое сохранение удаляется только после отдельного подтверждения.

Устанавливаемый PWA shell и Android wrapper намеренно оставлены для Этапа 5.
